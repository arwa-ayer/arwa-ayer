⚓ Guide vulgarisé · Kubernetes, Helm & CI/CD

Felix Simba n'est pas
de la magie. C'est un port.

Ce projet déploie deux applications (un front Angular et un back Spring Boot) sur Kubernetes, avec Helm comme plan de montage et GitLab CI comme chaîne de fabrication. Pour comprendre le mécanisme sans se noyer dans le YAML, on va tout comparer à un port de conteneurs : des entrepôts, des quais, une porte d'entrée gardée, et une chaîne de fabrication qui contrôle chaque conteneur avant de l'expédier.

01 · La carte du port

Où vit chaque morceau de l'application

Un cluster Kubernetes est un port autonome : une zone fermée où circulent des conteneurs. Une seule porte surveillée (l'Ingress) laisse entrer les visiteurs, qui sont ensuite dirigés vers les bons quais (Services), où travaillent des équipes (Pods) qui font tourner le vrai code.

1

Le navigateur charge l'application

Il appelle felix-simba-front.ctain-sbx.sacem.fr. L'Ingress reconnaît ce nom d'hôte et envoie la requête vers le Service front.

2

nginx sert la coquille Angular

Le Pod front répond avec index.html et les fichiers .js/.css. Angular prend alors la main dans le navigateur.

3

Angular appelle une API interne

Il tape sur /api/back/.... Ce n'est pas un nouveau nom d'hôte : c'est le même nginx qui intercepte ce préfixe.

4

nginx relaie vers le Service back

Il réécrit l'URL (/api/back/x → /felix-back/x) et la transmet à felix-simba-back-service:80, en DNS interne au cluster — aucun aller-retour public.

5

Le Pod back traite la demande

Spring Boot lit ses identifiants base de données dans le Secret, et peut lui-même appeler le service « processus » pour des données de référentiel.

02 · Le mécanisme

Comment Helm fabrique de vrais objets Kubernetes

Un chart Helm n'est pas un fichier YAML tout fait — c'est un gabarit. Il contient des trous ({{ .Values.xxx }}) que Helm remplit avec les réglages du moment, un peu comme un contremaître qui suit un plan et complète les blancs avec la fiche de commande du jour.

⚓ À retenir
  • Un chart = un plan réutilisable, valable pour sandbox, staging et production.
  • values.yaml = la fiche de réglages propre à chaque déploiement (souvent surchargée en ligne de commande).
  • _helpers.tpl = des fonctions (include "felix-simba-back.name" .) qui évitent de répéter la même logique dans chaque fichier.
  • Helm ne fait qu'assembler du texte puis l'envoie à Kubernetes — toute la vraie intelligence (créer un Pod, le surveiller) vient de Kubernetes, pas de Helm.

⚠ Le piège des variables protégées
  • Le job « Deploy to Sandbox K8s » vérifie explicitement que KUBECONFIG_SANDBOX n'est pas vide avant de faire quoi que ce soit.
  • Raison : dans GitLab, une variable CI/CD marquée « Protected » n'est transmise qu'aux branches elles-mêmes protégées. Sur une branche feature/* ou hotfix/* non protégée, la variable arrive vide — d'où le message d'erreur explicite plutôt qu'un échec Kubernetes opaque.
  • Autre détail malin : le tag de l'image suit une priorité en cascade — OVERRIDE_IMAGE_TAG s'il est fourni, sinon APP_VERSION calculé plus haut, sinon en dernier recours le hash court du commit (CI_COMMIT_SHORT_SHA).
04 · Fichier par fichier

Ce que chaque fichier fait vraiment

Cliquez sur un fichier pour déplier son explication, son rôle dans le port, et un extrait annoté.

back
Le lexique du capitaine
_helpers.tpl
+

Ce fichier ne crée aucun objet Kubernetes. Il définit des fonctions (define ... end) réutilisées partout ailleurs, pour ne jamais écrire deux fois la même règle. C'est le lexique commun que tous les autres fichiers du chart consultent.

4 fonctions définies
  • felix-simba-back.name — renvoie toujours le même nom court, utilisé comme préfixe.
  • felix-simba-back.namespace — utilise .Values.namespace s'il est renseigné, sinon retombe sur le namespace de la release Helm.
  • felix-simba-back.labels / selectorLabels — les labels « complets » (avec la version) contre les labels « de sélection » (jamais changés, car un Service ne doit jamais perdre de vue ses Pods).
  • externalEnv / ingressHost — piochent la bonne valeur selon .Values.environment (sandbox, staging, production).
extrait — sélection de la bonne URL selon l'environnement
{{/* Choisit l'URL du service processus selon l'environnement actif */}}
{{- define "felix-simba-back.externalEnv" -}}
{{- $env := .Values.environment -}}
{{- index .Values.externalServices $env | toYaml -}}
{{- end -}}
back
Le carnet de réglages
values.yaml
+

C'est la fiche de commande par défaut du conteneur : combien de répliques, quelle image, quelles ressources, quelles routes réseau. En pratique, presque tout ici peut être écrasé au moment du déploiement (--set).

Trois façons différentes d'injecter des variables d'environnement
  • env — valeurs fixes en clair (ex : TZ: Europe/Paris).
  • externalServices.<env> — URLs qui changent selon sandbox/staging/production.
  • secretEnv — ne contient pas la valeur, juste le nom de la clé à aller lire dans le Secret Kubernetes (mot de passe base de données, origines CORS…).
extrait — les trois sources de variables
env:
  SPRING_PROFILES_ACTIVE: "oracle"
  TZ: "Europe/Paris"

externalServices:
  sandbox:
    REFERENTIEL_BASE_URL: "http://felix-simba-processus-service...:80/felix-processus-back"

secretEnv:
  SPRING_DATASOURCE_PASSWORD: spring-datasource-password  # = un nom de clé, pas un mot de passe
Détail volontaire
  • image.tag est vide par défaut et obligatoire — le chart refuse de se déployer sans un tag explicite, pour ne jamais retomber accidentellement sur une vieille image.
back
L'équipage du conteneur
deployment.yaml
+

Le Deployment est la consigne donnée à Kubernetes : « fais toujours tourner replicaCount exemplaires de ce Pod, et remplace-le tout seul s'il tombe ». C'est lui qui fusionne les trois sources d'environnement du fichier précédent en une seule liste de variables réellement injectées dans le conteneur.

Deux médecins à bord (les probes)
  • readinessProbe — « es-tu prêt à travailler ? ». Tant que /felix-back/actuator/health ne répond pas, le Pod ne reçoit aucun trafic, même s'il est démarré.
  • livenessProbe — « es-tu toujours vivant ? ». Vérifiée en continu ; en cas d'échec répété, Kubernetes tue et relance le Pod tout seul.
extrait — fusion des trois sources d'environnement
env:
  {{- range $key, $value := .Values.env }}
  - name: {{ $key }}
    value: {{ $value | quote }}
  {{- end }}
  {{- range $key, $value := include "felix-simba-back.externalEnv" . | fromYaml }}
  - name: {{ $key }}
    value: {{ $value | quote }}
  {{- end }}
  {{- range $key, $secretKey := .Values.secretEnv }}
  - name: {{ $key }}
    valueFrom:
      secretKeyRef: { name: {{ $.Values.secretName }}, key: {{ $secretKey }} }
  {{- end }}
back
Le quai interne
service.yaml
+

Les Pods naissent et meurent (redéploiement, panne, mise à l'échelle) et changent d'adresse à chaque fois. Le Service est le quai fixe qui ne bouge jamais : il retrouve automatiquement les bons Pods grâce aux selectorLabels, et donne une adresse stable (felix-simba-back-service) à tous ceux qui veulent leur parler.

À retenir
  • Type ClusterIP — accessible uniquement depuis l'intérieur du cluster, jamais directement depuis Internet.
  • Le selector n'utilise jamais app.kubernetes.io/version, précisément pour ne pas perdre le Pod de vue lors d'une mise à jour d'image.

L'aiguilleur du front
nginx.conf
+

À l'intérieur du Pod front, c'est ce fichier — pas le Deployment — qui décide où va chaque requête. Quatre décisions à retenir :

RequêteComportementPourquoi
/healthzrépond 200 OK immédiatementc'est ce chemin que les probes Kubernetes appellent en boucle

Un bug corrigé, laissé en commentaire

Le fichier contient un commentaire CORRECTIF : appeler /felix-simba-front/ (avec le slash final) déclenchait autrefois une boucle de redirections 302, car la règle réécrivait l'URL vers elle-même. La correction sépare explicitement le cas « sans slash » (redirection) du cas « avec slash » (réécriture directe vers index.html).

extrait — le proxy vers le back
location /api/back/ {
    rewrite ^/api/back/(.*)$ /felix-back/$1 break;
    proxy_pass http://felix-simba-back-service:80;
    proxy_set_header Host $host;
    proxy_read_timeout 120s;
}
05 · Lexique du port

Le vocabulaire, sans jargon

Pod

La plus petite unité qui tourne dans le cluster : un ou plusieurs conteneurs qui vivent et meurent ensemble. C'est « l'équipage » à bord.

Deployment

La consigne permanente qui dit combien de Pods identiques doivent exister, et les remplace automatiquement s'ils tombent.

Service

Une adresse réseau stable qui pointe toujours vers les bons Pods, même quand ceux-ci changent. Le quai qui ne bouge jamais.

Ingress

La porte d'entrée du cluster : associe un nom de domaine public à un Service interne, avec HTTPS en option.

Namespace

Une cloison à l'intérieur du port qui isole des groupes de ressources entre eux (ex : sandbox vs production).

Secret

Un coffre-fort Kubernetes pour les données sensibles (mots de passe, tokens), lu par les Pods au démarrage plutôt qu'écrit en clair dans le chart.

Chart Helm

Le plan de montage réutilisable d'une application : des gabarits YAML plus une fiche de réglages par défaut.

Release Helm

Une instance concrète d'un chart, déployée avec un nom donné dans un cluster donné (ex : felix-simba-back en sandbox).

Named template

Une fonction réutilisable définie une fois (_helpers.tpl) et appelée partout ailleurs avec include, pour éviter la répétition.

Probe

Un contrôle de santé automatique. « readiness » = prêt à travailler, « liveness » = toujours vivant, « startup » = a fini de démarrer.

Tag d'image

L'étiquette qui identifie précisément quelle version du code tourne dans le conteneur Docker — le numéro de série du conteneur.

Pipeline CI/CD

La chaîne automatisée d'étapes (stages) qui transforme du code source en application déployée, avec des contrôles à chaque poste.

Variable protégée

Un réglage GitLab CI marqué sensible, transmis uniquement aux branches elles-mêmes protégées — absent sur une branche feature/* ordinaire.

Rolling update

Une mise à jour progressive : les nouveaux Pods démarrent avant que les anciens ne s'arrêtent, pour zéro interruption de service.

Ce guide vulgarise les fichiers Helm, Kubernetes, nginx et GitLab CI du projet Felix Simba. C'est une simplification pédagogique : pour le comportement exact, la référence reste le code source des charts et du pipeline.
